# T2.2 TF 延迟采样测试指南

这套工具测量腿部 TF 发布端与 VOA Bridge 接收端之间的延迟。当前交付只在开发虚拟机完成代码集成和离线验证，尚未部署、连接 Jetson 或进行实机采样。

工具不调用 ROS 控制接口，不启停业务节点。实机部署和为加载新代码而重启节点，需要用户另行授权。整个采样过程必须保持 DISARMED，不发送导航目标。

### 默认关闭与旧请求保护

- 节点初始化时必须存在有效的 `/tmp/lite3_t22_enable`，才会创建 Probe 和 writer 线程。只有 `start.json` 不会开启诊断；缺少或无效的启用标记时没有记录线程，也没有业务数据写入。
- 启用标记包含本次 Jetson `boot_id` 和随机 `enable_id`。请求必须使用相同的 boot、enable 代号，且创建时间严格晚于两个 Probe 的初始化时间。遗留的请求不会让重新启动的节点自动录制。
- 两个节点必须在标记建立后由操作者启动。先启动节点、后创建标记不会动态激活已有 Probe，`start` 会因缺少 ready 状态而拒绝。
- 没有 `start.json` 时，启用的 Probe 只更新每秒一次的小型 ready 状态，不记录业务帧。
- 本轮开发操作没有执行任何实机部署命令；本地测试通过也不代表 Jetson 已加载修改。

## C. 实机采样：保持 DISARMED

下列步骤是后续实机操作说明，**本轮未执行**。

1. 操作者通过现有状态显示确认 DISARMED，现场不发送目标或速度。工具不会调用 ARM、DISARM 或状态服务，也不会代替操作者判断机器人安全状态。
2. 在加载诊断代码的两个节点启动之前，执行：

```bash
cd /home/ysc/lite3_patrol_project
python3 tools/t22/t22_capture.py enable-diagnostics
```

3. 在另行授权后，由操作者用原有流程加载两个业务节点，保持不 ARM。然后读取诊断状态：

```bash
python3 tools/t22/t22_capture.py status
```

`ready.leg` 和 `ready.voa` 应各有且只有一个新鲜的记录器，`state` 为 `waiting`，没有 `recorder_error`。ready 超过 5 秒没有刷新，或者出现同角色的多个新鲜进程，`start` 会拒绝开始。

4. 创建统一的 45 秒采样请求：

```bash
python3 tools/t22/t22_capture.py start --duration 45
```

输出 JSON 包含自动生成的 `capture_id`、本机 boot、单调时钟 `issued_ns` / `start_ns` / `end_ns`。默认预留 10 秒，两端接受同一个未来窗口。`duration` 只允许整数 30～60 秒；`--lead-seconds` 可选 3～60 秒。工具不调用 ROS、不增加订阅、不启动或重启节点。

5. 保存该 `capture_id`，随后查询状态：

```bash
python3 tools/t22/t22_capture.py status --capture-id 实际采样ID
```

状态依次是 `scheduled`、`recording`、`window_ended`。45 秒采样默认大约在命令发出 55 秒后结束，再留出约一秒完成 writer 收尾。确认两个结果文件均出现 `finished=true`，`both_finished=true`，且没有 `recorder_errors`。`window_ended` 仅表示时钟到达期限，不等于文件已收尾。`both_finished` 也不等于统计质量通过，仍需离线分析检查掉记录、匹配和异常。

### 控制文件和结果文件

```text
/tmp/lite3_t22_enable
/tmp/lite3_t22_start.json
/tmp/lite3_t22_ready_leg_<PID>.json
/tmp/lite3_t22_ready_voa_<PID>.json
```

使用 `python3 tools/t22/t22_capture.py help` 查看总帮助，`help start` 或 `start --help` 查看子命令帮助；帮助命令不读写控制状态。

### 连续做多轮采样

一次完整采样结束后，只要标记保持有效、两个记录器还在等待，可以再次运行 `start --duration 45`，每次自动使用新 ID，无需为每轮重启节点。不要在上一轮结束和最终写入之前创建下一轮请求。

## D. 数据收集：在开发虚拟机执行

使用已有 SSH Host Alias 或用户明确指定的 `user@host`。工具没有预设机器人 IP、账号、密码或密钥；不会修改 SSH 设置。以下变量由操作者填入：

```bash

```

此步骤会通过 SSH 只读检查 Jetson `/tmp` 的两个 JSONL，再用 SCP 复制到开发端 `$T22_OUTPUT/$T22_ID/`。复制后核对字节大小和 SHA-256，保留 Jetson 原始文件，生成：

```text

```

如果已有 SSH 配置需要特定现有私钥，可以加 `--identity 路径`；工具不创建或替换任何密钥。首次主机认证或用户登录问题应由操作者使用已有连接流程处理。

## E. 离线分析

```bash
python3 tools/t22/analyze_t22.py "$T22_OUTPUT/$T22_ID"/*.jsonl
# 可选：另存一个新报告，已有文件拒绝覆盖
python3 tools/t22/analyze_t22.py "$T22_OUTPUT/$T22_ID"/*.jsonl \
  --json-output "$T22_OUTPUT/$T22_ID/analysis_review.json"
```

`--json` 将完整报告输出到终端。退出码：`0` 表示完整数据，`1` 表示部分结果，`2` 表示输入拒绝或工具错误。收集工具也采用这套退出码；控制工具的命令失败返回 `2`。

`complete` 只表示记录完整性通过，不是机器人时延验收通过。必须结合每项 N 判断统计意义；样本过少时只能作为线索，不能凭一个平均数判定发布端或接收端就是根因。

### 各项时间的含义

所有 T2～T4 时间点在对应业务进程中用 Jetson `time.monotonic_ns()` 记录，单位为 ns。两端用原始 TF Header 的整数纳秒 `source_stamp_ns` 对齐，禁止用浮点秒作连接键。

| 指标 | 解释 |
| --- | --- |
| `T2_enter_to_valid` | 输入回调进入到原有校验通过；统计每条有效输入，包含随后被覆盖的输入 |
| `T2_valid_to_T3a` | 实际被发布消息的校验完成到定时器进入 |
| `cache_to_T3a` | 实际被发布消息的缓存更新时间到定时器进入 |
| `timer_interval` | 所有活跃窗口内定时器进入时刻的间隔，即使该轮没有新消息可发布也记录 |
| `timer_interval_minus_50ms` | 间隔减去既有 50 ms，负值是正常的提前/抖动观测，不自动视为异常 |
| `deepcopy` | 原有深拷贝调用耗时 |
| `sampled_publish_call` | 辅助 Odometry 发布调用前后，不等于接收端收到 |
| `T3a_to_T3b` | 定时器进入到辅助发布返回，包含前面的检查、graph clock、复制等 |
| `TF_build` | 辅助发布返回到 sendTransform 进入，包含构造 TF 及必要测时开销 |
| `T3c_to_T3d` | sendTransform 本地调用耗时；T3d 不是送达确认 |
| `T3d_to_T4a` | 发布调用返回到该 TF Listener 回调进入；包含 DDS、接收队列、调度等，不能统称网络延迟 |
| `T4a_to_T4b` | Listener 进入到当前腿部 TF 插入调用开始，包括同一消息内前面 TF 的处理 |
| `T4b_to_T4c` | 原有 Buffer.set_transform 调用耗时 |
| `T3c_to_T4c_call_return` | sendTransform 进入到 Buffer 插入调用返回的观测总差值 |
| `listener_callback` | 包含腿部 TF 的整个原有 Listener 回调执行时间 |
| `T1_to_T2` | 未测量：C++ 实际 publish 时间没有埋点，N=0、各延迟为 null，不能补零 |

每项均有样本数、mean、P50、P95、最大值、严格超过 20/50/100 ms 的次数和负值数量。首个 tick 没有前一轮可供比较，其 interval 为 null，正常不计入间隔统计。

`T4a < T3d` 可以发生：发送调用尚未返回，接收回调已经开始。分析器保留负值；若 T4a 甚至早于 T3c，则标为不合理的跨进程负差值。不要把所有负数截成零。

Buffer 调用不抛异常只记录为 `returned_no_exception`，并带 `queryability_checked=false`。某些 TF2 实现可能在内部拒收后只打印错误，因此本轮不会把调用返回冒充 BufferCore 接受或“该时刻必然可查询”。工具不为此增加 TF 查询，也不改变原有查询次数。

### 查询失败证据

- `map_grid`：原有 `map ← base_link` 精确 GridMap 时间查询。
- `leg_anchor`：`robot_odom ← leg_base_link` 在 NDT anchor 时间的查询。
- `leg_grid`：同一腿部链路在 GridMap 时间的查询。

每次失败都保留分类计数，区分异常类和 future/past/other。原始异常不替换、不吞掉，沿用原业务捕获和传播行为。详细样例每个查询段每秒最多 20 条；计数包含所有重试，不是不同 GridMap 的去重帧数。

样例包含 GridMap stamp、当前源年龄、实际请求 stamp、异常类及原文。若异常原文给出 latest TF 时间，分析器提取并计算差额；原文没有的时间保持 null。`last_set_returned_stamp_ns` 只是最近一次插入调用返回的记录，**不是 Buffer 内真正的最新时间**。阶段计数独立输出，避免把 NDT 精确查询的 future 次数误当成腿部 TF 的 future 次数。

### 怎样判断发布慢还是接收慢

- `timer_interval` 经常显著大于 50 ms，或 `T2_valid_to_T3a` / 复制 / 发布调用时间变大：调查发布端调度和本地执行；latest-value 设计下，缓存等待不能直接当成每条输入固定等待 50 ms。
- 发送端正常，但 `T3d_to_T4a` 大：DDS 与接收回调调度的合计延迟，需要进一步证据才能拆分。
- `T4a_to_T4b` 大：调查 Listener 内的处理；`T4b_to_T4c` 大：调查 Buffer 调用。不能仅凭最终 TF 频率判定其中哪一段慢。
- 两边测量都正常但 `leg_grid` future 仍多：重点检查不同数据流的采样相位与时间覆盖，不能以最新 TF 或改写 Header 代替合法历史查询。
- 本次没有新增 CPU 调度探针或 RMW 追踪，不能直接从时间差宣称 CPU 竞争或网络是唯一根因。

### 完整性与异常数据

分析前核验 capture、boot、enable 代号、start、duration、两个角色、最终 finished、窗口覆盖、丢弃计数和文件格式。身份或窗口不一致拒绝合并；缺一端、截断、写入错误、掉记录、歧义 stamp、非合理负数或未配对 stamp 都标为 `partial`。窗口边缘也可能出现单端样本，仍如实标记，不静默删除后宣称完整。

报告输出 `unmatched_tx`、`unmatched_rx`、重复 source_stamp、`dropped_rows`、`recorder_error`、未来外推调用数和按查询段分布。重复 stamp 不任选一条进行配对。部分数据可以辅助排查，但不能作为完整统计通过的证据。

## F. 测试结束

确认两端文件已经结束，最好先收集，再在 Jetson 执行：

```bash
python3 tools/t22/t22_capture.py cleanup
```

它只移除启用标记和采样控制文件，不删除 JSONL、ready 状态或业务文件，不关闭节点。记录器在下次约一秒轮询时停止诊断线程。采样尚未结束、或窗口结束但两端还未完成最终写入时，默认拒绝。

确实需要中断诊断时，操作者可以明确使用 `cleanup --force`；这是中断诊断记录，不是 DISARM，不改变机器人状态。提前结束的文件不会写成 `finished=true`。磁盘完全不可写时，错误可能无法写入 JSONL；应结合 ready 状态和文件缺失/截断检查，不能把没有错误行理解成没有记录器故障。

cleanup 后重新 enable 会生成新的启用代号；已经关闭的 Probe 不会重新自启，下一次需要经授权重新加载节点。旧请求在新 Probe 启动后也不会自动录制，必须重新运行 start。

## 容量与性能边界

每端 deque 上限 4096 条，writer 每秒批量排空。容量是**待写队列容量，不是整个 45 秒会话的记录条数上限**。

按约 200 Hz 腿部输入和既有 20 Hz 发布估算，腿端每秒约 `200 leg_input + 20 leg_tick + 20 leg_tx = 240` 条，45 秒约 10800 条、60 秒约 14400 条，分批写入，正常一秒约 240 条排队。4096 条理论可覆盖约 17 秒不排空的积压；这只是频率估算，不是对 CPU 或磁盘卡顿的保证。

接收端按 20 Hz 腿部 TF 估算约 `20 leg_rx + 20 listener_callback = 40` 条/秒，另有三个查询段各最多 20 条/秒的失败样例，即约 100 条/秒、60 秒约 6000 条。若真实频率或消息批次分布改变，应按实测复核。队列满或争用诊断锁时，业务回调不等待，而是计入 `dropped_rows`，分析标为不完整。

高频回调只做少量时间记录与计数，不写 JSONL、不读取控制文件、不计算分位数。writer 在业务锁之外进行 JSON 编码和文件 I/O；诊断锁只保护短时快照，业务记录以非阻塞方式获取。诊断失败仅停用诊断，不改变原有 ROS API 次数、返回或异常传播。未启用时没有 writer，TF2 不使用包装子类，没有全局 monkey patch。

JSONL 包含 recorder bookkeeping 和 writer 线程 CPU 时间，以及整个业务进程 CPU 时间。前两项是可测部分的下界，不能覆盖埋点取时、包装入口等全部成本；进程 CPU 包含业务，不能直接当作诊断 CPU。实机额外负载、磁盘写入、Foxy API 兼容性和 30～60 秒自然静止运行仍需授权后的 DISARMED 采样，与未启用诊断的基准比较。本地测试不能证明 Jetson 上没有测量扰动。

`bookkeeping_thread_cpu_ns` 是本窗口活跃记录的累计 CPU；`writer_thread_cpu_ns` 从接受本次请求起累计，包含开始前预留时间，且最终批次的写入成本尚未计入。`process_cpu_ns` 是整个进程累计值，metadata 中的 `process_cpu_base_ns` 提供请求接受时基线。分析报告保留 `observed_elapsed_ns`，计算 CPU 比例时应使用相同观测区间，不能把进程历史累计值直接除以 45 秒。
